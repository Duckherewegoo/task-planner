# ADR-0002: 转向全链路异步（已被 ADR-0001 取代）

- Status: Superseded by ADR-0001
- Date: 决策 2026-09-28（口述时刻 ~15:42）/ 被推翻 2026-10-13
- Superseded by: ADR-0001（异步边界分层）

  - 关键 commit：`7a2c736`（2026-10-13 20:14，DB 迁移同步 pymongo，推翻落地）


> **阅读提示**：本文冻结在 2026-09-28 的决策时刻，记录"当时为什么这样想、

## Context

**项目阶段**：Dash 迁移已完成（2026-08-15，见 ADR-0003），Gradio 遗留清除中。
项目从"能跑的原型"转向"考虑部署形态的工具"。

**触发因素**：三个动机叠加，权重递减。

1. **战未来（主要）**：万一以后部署到服务器、或 K8s 多副本部署，
   同步阻塞会成为并发瓶颈。当时没有具体的多用户场景，
   判断依据是"如果将来要，现在改比将来改便宜"。
2. **认知/审美（次要但真实）**：认为"成熟的 agent 应该用异步"——
   LLM 调用本质是长耗时 IO，异步是这类系统的"正统形态"。
   这是一个未经验证的行业直觉，不是需求驱动。
3. **当时已存在的混乱（催化）**：DB 层代码质量参差——
   原生 async 函数、纯同步函数、以及"同步函数包一层 `async def` 再 `asyncio.wait`
   强行异步"三种写法并存。与其逐个修补，不如统一到异步重写一遍。

**已知约束（当时认知）**：

- Dash 4.4.1 的 async 回调支持尚可（`dash[async]`）
- Motor 是 MongoDB 官方异步驱动
- AsyncOpenAI 已稳定

**当时不知道的**：Dash Flask backend 的 event loop 在同一 thread 内会变化
（A→B→C）。这个事实在 2026-10-13 才通过实测发现，详见 ADR-0001 的 Context。

## Decision

全面转向异步：

- **业务函数**：全部改为 `async def`
- **DB 层**：MongoDB 驱动从同步/ODM 切换到 **Motor**（`AsyncIOMotorClient`）
- **LLM 层**：使用 **AsyncOpenAI** + `httpx.AsyncClient`
- **后台任务**：`asyncio.create_task` 在回调的 event loop 上创建 worker / cleaner
- **并发控制**：`asyncio.Lock` / `asyncio.Semaphore` 模块级持有

**核心假设**：**"异步客户端可以绑定到进程内某一个稳定 loop 上长期复用。"**
这个假设在 2026-10-13 被实测证伪——那是 ADR-0001 的内容。

## Alternatives Considered

**A. 保持全同步** —— 否决
- 与"战未来"动机冲突
- LLM 调用 60s 超时会阻塞 Dash worker，用户体验差
- 当时认为这是"不成熟"的方案

**B. 分层异步（仅 LLM 异步，DB 同步）** —— 当时未考虑
- 这正是 ADR-0001 最终采纳的方案
- 2026-09-28 的认知里，"要么全同步要么全异步"是默认框架，
  混合形态被认为"不够干净"——事后看这是美学判断压过了工程判断

**C. 全异步 + 按 loop 缓存客户端** —— 当时未考虑
- 需要先知道"loop 会变"这个事实
- 知道后成为 ADR-0001 的方案 C（暂缓项）的候选路径

## Consequences

### 当时预期的收益

- 同步阻塞消失：LLM / DB 调用期间 worker 不空转
- 并发吞吐提升：多用户/多任务场景下更从容
- 为部署形态演进（多副本、ASGI）预留空间
- DB 层三种写法归一，消除既有混乱

### 实际执行中出现的问题（决策落地区间 2026-09-28 ~ 2026-10-12）

> 这一段在 ADR 规范里本不该出现（Consequences 记录"预期的后果"），
> 但本决策的落地过程本身产生了值得记录的事实，故单列。它不属于"事后反思"，
> 而是"执行史实"。

- **DB 层混乱未消除，反而加深**：统一到异步的过程中，
  产生了"同步函数包 `async def` + `asyncio.wait`"这类强行异步的中间形态，
  最终形成三种写法并存的局面（原生 async / 纯同步 / 伪异步）。
- **跨 loop 报错开始零星出现**：`Event loop is closed`、
  `... is bound to a different event loop` 在测试与运行时偶发，
  当时归因为"pytest-asyncio 配置问题"，未追到根因。
- **后台任务被静默取消**：worker / cleaner 有时不执行完成，
  当时认为是"任务本身出错"，未意识到是回调 loop 销毁导致。

以上三条在 2026-10-13 的实测中被统一解释，构成 ADR-0001 的推翻依据。
